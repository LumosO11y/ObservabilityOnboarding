1. Elaborate on the history before OpenTelemetry, how it was created and why?
A: Before we had sophisticated tools like OpenTelemetry, developers and operators used basic techniques to monitor their systems. 
   Two key tools were logs and metrics, However, as systems grew in complexity, 
   especially with the rise of cloud computing and microservices, logs and metrics alone were insufficient.
   Before OTEL two projects lead the observability world: OpenCensus and OpenTracing:
	* OpenTracing - set of vendor-neutral APIs and instrumentation for distributed tracing, allowing developers to monitor application performance across microservices.
	* OpenCensus - a set of open-source libraries, originally started by Google, designed to collect application metrics and distributed traces, enabling developers to monitor microservices and application performance
   It became clear to the industry that two projects (OpenTracing and OpenCensus) were serving similar purposes but with slightly different approaches and goals. 
   While OpenTracing offered a standard for tracing, OpenCensus had a broader scope, aiming to unify both tracing and metrics. 
   Many companies and contributors in the open-source community felt that having two competing standards caused fragmentation.

2. What is OpenTelemetry (aka OTel)?
A: open-source CNCF observability framework providing a vendor-neutral set of APIs, SDKs, and tools to instrument, generate, collect, and export telemetry data—traces, metrics, and logs—to analyze software performance.

3. How does OpenTelemetry relate to Observability?
A: OpenTelemetry the lack of a standard for how to instrument code and send telemetry data to an Observability backend. 

4. How did OpenTelemetry revolutionize the monitoring/observability world?
A: OpenTelemetry (OTel) revolutionized the monitoring and observability world by transforming how telemetry data (logs, metrics, and traces) is collected, moving from a fragmented, vendor-locked landscape to a unified, open-standard approach.

6. Pick 3 OpenTelemetry concepts and explain them.
A: Glossary - This glossary defines terms and concepts that are new to the OpenTelemetry project, and clarifies OpenTelemetry-specific uses of terms common in the observability field.

   Collector - The OpenTelemetry Collector is a vendor-agnostic proxy that can receive, process, and export telemetry data. 
	       It supports receiving telemetry data in multiple formats (for example, OTLP, Jaeger, Prometheus, as well as many commercial/proprietary tools) and sending data to one or more backends.
	       It also supports processing and filtering telemetry data before it gets exported. It is built from:
			* Receivers - Receivers collect telemetry data from various sources and formats. For more information on how to configure receivers, see the Collector configuration documentation.	
			* Processors - Processors transform, filter, and enrich telemetry data as it flows through the pipeline. For more information on how to configure processors, see the Collector configuration documentation.
			* Exporters - Exporters send telemetry data to observability backends and destinations. For more information on how to configure exporters, see the Collector configuration documentation.
			* Connectors - Connectors connect two pipelines, acting as both exporter and receiver. For more information on how to configure connectors, see the Collector configuration documentation.
			* Extensions - Extensions provide additional capabilities like health checks and service discovery. For more information on how to configure extensions, see the Collector configuration documentation.
		
   Sampling -  A methods where traces either sampled or not sampled(which means they are either processed or exported). 
	       With sampling, you can reduce costs of observability without losing visibility, you can sample traces with two methods:
		* Head Sampling - sampling technique used to make a sampling decision as early as possible. A decision to sample or drop a span or trace is not made by inspecting the trace as a whole.
		* Tail Sampling - sampling technique where the decision to sample a trace takes place by considering all or most of the spans within the trace. Tail Sampling gives you the option to sample your traces based on specific criteria derived from different parts of a trace, which isn’t an option with Head Sampling.

7. Write 3 pros and 3 cons of OpenTelemetry.
A: Vendor Neutrality & No Lock-in: OTel allows you to instrument your code once and send telemetry data to any backend, including Jaeger, Prometheus, or commercial vendors. You can easily switch backend providers without re-instrumenting applications.
   Unified Data Collection: It provides a single, open standard for collecting traces, metrics, and logs, reducing the need for multiple, fragmented vendor agents.
   High Flexibility and Customization: Each OpenTelemetry Commponnents is configurable as fuck  

   Complexity and High Effort: Setting up and managing OpenTelemetry—particularly collector pipelines—is complex and requires significant engineering expertise compared to proprietary all-in-one agents.
   No Built-in Backend or Visualization: OpenTelemetry is only for data collection, not storage or visualization. You still need to pair it with a separate tool for dashboarding and alerting, as it does not provide analytics.
   While OpenTelemetry captures a wide range of telemetry data, it might lack some advanced features specific to vendor tools.
